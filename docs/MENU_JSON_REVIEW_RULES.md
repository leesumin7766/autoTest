# 메뉴트리 외부 LLM 흐름과 실제 검토 규칙

① 공통 지침을 LLM에 한 번 등록 → ② 화면 수집 완료 후 제품별 프롬프트 복사 → ③ LLM JSON 응답 가져오기 → ④ 검토·Excel 출력.

공통 지침 MD에는 작성 규칙·예시·출력 스키마를 둔다. 제품별 프롬프트에는 등록된 지침 버전, 해당 제품의 작성 요청, 요청 ID, 제품명·근거·웹 구조를 둔다. 공통 본문을 다시 붙이지 않는다. 화면의 로컬 LLM 자동생성 버튼은 숨긴다.

## 가져오기에서 거부하는 조건

- JSON 파싱 실패 또는 비어 있는 rows. UI는 바깥쪽 Markdown 코드 블록을 제거한 뒤 JSON.parse한다. 해설이 JSON 밖에 붙으면 실패한다.
- requestId가 현재 작업·고정 입력·지침 버전으로 계산한 요청과 불일치한다.
- 기능 행이 객체가 아니거나 1~2,000개 범위를 벗어난다.
- 각 evidenceRefIds가 1~8개 배열이 아니거나, 현재 요청에 없는 번호·중복 번호를 포함한다. 서버가 sourceId·원문·메뉴 연결을 복원한다.
- 같은 menuPath·functionName·menuDescription의 중복 행. 기능명·설명은 공백을 제거하여 중복을 판별한다.
- menuPath가 배열이 아니거나 3개를 초과한다. 각 경로는 비어 있지 않은 문자열, 120자 이하이며 '-'를 허용하지 않는다. 제품명과 마지막 기능명은 menuPath에 넣지 않는다.
- functionName이 비었거나 160자를 넘는다. menuDescription이 비었거나 600자를 넘거나 마지막이 정확히 '기능'이 아니다. 따라서 '기능입니다', '기능.'도 현 구현에서는 거부된다.
- location이 HEADER/FOOTER/SIDEBAR/CONTENT/UNKNOWN 이외다. 생략하면 서버 기본값은 UNKNOWN이다.
- reviewNotes가 제공됐는데 배열이 아니거나, 최종 메모가 8개를 넘거나 개별 메모가 500자를 넘는다. 생략한 메모는 외부 응답 복원 단계에서 배열로 보완한다.
- 선택적으로 준 rowId가 비었거나 중복되거나 80자를 넘는다. 생략하면 서버에서 생성한다.
- 최종 원문 근거가 1~8개 범위를 벗어나거나, 인용문이 500자를 넘거나, 고정된 원문에 실제로 존재하지 않는다. 정상 근거 번호 응답은 서버가 원문을 복원하므로 LLM이 인용문을 다시 쓸 필요가 없다.
- 생성 중인 작업에 가져오거나, 다른 저장으로 revision이 변경된 오래된 화면에서 가져온다.

스키마에 적힌 모든 required·additionalProperties 규칙을 JSON Schema 엔진으로 일괄 검사하는 구조는 아니다. 위 Java 코드와 UI 검사가 실제 거부 기준이다. 불필요한 필드는 일부 무시되거나 서버에서 복원한다.

## 거부가 아닌 배치·경고 처리

- 관찰된 웹 메뉴 근거가 일관되면 그 실제 경로를 적용한다. LLM이 작성한 다른 경로를 그대로 믿지 않는다.
- 화면 위치가 없거나 서로 다른 메뉴 경로를 섞어 연결하면 경로·연결을 비우고 UNASSIGNED, included=false로 보존한다. 사용자가 기존 웹 경로를 선택하여 배치 검토할 수 있다.
- 웹 우선 구조에서 문서 근거가 없으면 MENU_OBSERVATION으로 분류한다. TC 생성 대상 기능 행과 구분한다.
- 문서만 있는 기능, 불완전한 화면 확인, 참조되지 않은 문서 구간은 검토 정보다. 이것만으로 JSON 전체를 반려하지 않는다.
- 의미적 일치·기능 누락은 자동 검증 완료로 표시하지 않는다. 참조 현황은 문서 구간 단위이며 의미적 기능 커버리지가 아니다. 가져오기 검사는 Jev·LLM 재판정이 아닌 코드 기반이다.

## 편집·최종 승인 제한

- 편집은 기존 근거가 있는 행만 수정·분리할 수 있다. 임의의 새로운 근거 행을 만들 수 없다.
- 현재 문서가 Jev 검증을 통과해야 하며, 작업의 문서 버전과 일치해야 한다.
- DRAFT/APPROVED 상태만 검토 가능하며 MOCK 또는 PARTIAL 출력은 최종 승인할 수 없다.
- 최종 승인에는 포함된 행이 최소 하나 필요하다. 문서 변경이나 revision 충돌도 승인을 차단한다.

실제 반려 원인을 특정하려면 그 요청의 JSON과 오류 코드·메시지를 대조해야 한다. 위 조건 목록만으로 특정 응답의 실패 원인을 단정하지 않는다.
