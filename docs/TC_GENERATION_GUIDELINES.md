# TC 생성 기준

## 목적

TC는 제품 동작이 요구사항에 맞는지 반복해서 시험하고, 기대 결과와 실제 결과의 차이에서 결함을 찾기 위한 실행 가능한 절차다. 문서 요약, 메뉴 목차 확인, 문구 복사는 TC로 취급하지 않는다. 생성 결과는 초안이며 시험 결과나 실제 결함 판정으로 표시하지 않는다.

## 같은 결과물에 포함하는 두 검증 유형

### 제품 동작 (`PRODUCT_BEHAVIOR`)

- 실제 제품의 기능, 입력, 상태, 출력이 제공 문서에 명시된 동작과 일치하는지 시험한다.
- 한 TC는 하나의 판정 목적을 가진다. 사전조건, 시험자 동작, 입력, 관찰 가능한 기대 결과를 구체적으로 쓴다.
- 긍정·부정·경계·권한·오류·복구 시험은 문서 근거가 있을 때 만든다. 값, 성공 동작, 오류 메시지를 지어내지 않는다.

### 문서 적합성 (`DOCUMENT_CONFORMANCE`)

- 제품설명서와 사용자매뉴얼의 제공 여부를 각각 확인한다. 이는 LLM이 문서에서 추측하는 내용이 아니라 프로젝트 공통 기준으로 추가한다.
- 시험 시 제품의 공식 배포 패키지나 공급 자료를 확보하고, 문서가 시험대상 제품에 해당하는지 확인한다. 접수 시 분석용으로 매뉴얼 파일이 올라왔다는 사실만으로 실제 공급 자료의 제공 여부가 입증되지는 않는다.
- 입력 문서가 필수 정보를 제공한다고 명시하면, 해당 정보를 제품설명서/사용자매뉴얼에서 찾고 정확성·완전성을 판정하는 TC를 추가할 수 있다. 적용 조건이나 요구 기준이 분명하지 않으면 담당자 확인 항목으로 남긴다.
- 제품 동작 시험과 문서 내용 점검을 한 TC에 섞지 않는다.

## 문서 근거와 문서 역할

- 기능리스트는 기능 이름과 범위를 찾는 데 쓴다.
- 사용자매뉴얼은 절차, 입력, 화면, 상태, 명시된 기대 동작을 찾는 데 쓴다.
- 시험합의서는 시험대상 식별, 범위, 환경, 제약 및 적용 조건을 찾는 데 쓴다. 행정 절차나 시험 협조 사항을 제품 기능으로 만들지 않는다.
- 현재 생성기는 제품 동작 TC를 사용자매뉴얼에서만 생성한다. 기능리스트와 시험합의서 청크는 단독으로 시험 결과를 뒷받침하지 않으므로 LLM 생성 호출에서 제외한다.
- 기능리스트만으로 실제 절차·기대 결과를 상상하지 않는다. 매뉴얼에 명시된 제품 동작을 시험 근거로 우선한다.
- 시험기관·인증·신청기업·보고서 제출 등 시험 행정 절차는 제품 기능 TC로 만들지 않는다.
- 원문 인용은 추적 근거이지 의미 검증의 대체물이 아니다. 기대 결과가 인용문으로 뒷받침되지 않으면 성공/실패 동작을 단정하지 않고 검토 메모를 쓴다.
- 상충·불명확·추출 손상은 제품 결함으로 단정하지 않고 담당자 검토 대상으로 표시한다.
- 사전 검증 경고는 원문 추출·검토에 대한 신호이며, 프로그램 결함의 근거로 사용하지 않는다.
- 제품 문서 제공 여부 기준은 프로젝트 정책 출처로 표시하고 원문 인용과 구별한다.

## 결과 및 결함 예시

- 생성 시 결과는 빈 상태다. 제품을 실행하거나 시험했다고 주장하지 않는다.
- 결함요약·정도·내용은 실패했을 때 담당자가 작성할 예시다. 실제 발견 결함과 섞지 않는다. 심각도 기준이 확정되지 않은 경우 `검토 필요`로 둔다.
- 자동화 후보 표시는 실행 가능성에 대한 검토값일 뿐, 자동화 구현이나 시험 실행을 뜻하지 않는다. 보안·성능 및 문서 적합성은 수동 시험으로 둔다.

## 생성 전후 품질 확인

- 중복 시나리오와 동일 동작의 표현 변형을 검토하고, 시험 조건이나 기대 결과가 실질적으로 다를 때만 별도 TC로 유지한다.
- 근거가 없거나 제품과 무관한 청크는 TC 0건을 허용하며, 한 청크에서 최대 1건만 생성한다. 근거가 없는 청크는 LLM 호출을 생략한다.
- 각 TC의 기능 경로, 조건·입력, 절차, 기대 결과, 분류, 근거, 적용 가능성을 담당자가 검토한다.
- 전체 문서를 대상으로 한 기능 통합·유사 중복 검토 및 자동 품질 게이트는 후속 개선 대상이다. 현재 원문 인용 검사는 인용 위치가 맞는지만 보장한다.
